# Filatrix ERP Web 五模块原型冻结与数据库实施蓝图

更新时间：2026-07-28  
状态：原型冻结检查基线；不是数据库建表脚本  
权威顺序：`erp-web-prototype-blueprint.md`、`erp-web-business-fact-model.md` 高于本文件；本文件负责把两份权威文档的现行结论汇总为实施入口。

## 1. 冻结范围与结论

本轮冻结销售、采购、仓库、生产、质检五个业务模块。基础资料、账号权限、通知、附件和审计是公共支撑；电商继续作为后续渠道集成；独立财务模块不在当前系统范围。

“冻结”表示：

- 正常流、异常流、数量守恒、角色动作和跨模块交接已经形成可测试合同。
- 新需求不得继续通过增加复合状态、跨模块跳转或前端临时数组解决。
- 现有 JSON 只用于原型演示和回归，不作为数据库表结构。
- 进入数据库实施前可以修复缺陷、响应式和可访问性问题，但不再无依据扩张业务流程。

## 3. 跨模块主链冻结

### 3.1 销售履约

`报价 → 销售订单 → 库存预留/生产需求 → 销售交付安排 → 仓库销售出库 → 销售确认签收`

- 销售订单确认形成履约需求，库存覆盖、生产覆盖和未覆盖数量独立展示。
- 交付安排是销售事实；仓库销售出库任务是自动承接的执行事实。
- 仓库出库原子扣减库存、消费销售预留并写流水，销售只读接收结果。

### 3.2 采购入库

`采购申请 → 采购订单 → 仓库登记到场/拒收 → 来料质检或免检 → 仓库部分/分仓正式入库`

- 到场、质检、可入库、正式入库、拒收、异常暂收和关闭待收余量是独立数量。
- 订单冻结 5% 自动超收容差；超过容差走拒收或异常，短收余量由采购决定继续收货或关闭。
- 批次管理物料第一次正式入库时生成批次；免批次物料始终使用空批次。

### 3.3 生产物料与执行

`生产任务 → 备料需求系统评估 → 缺口采购申请 → 生产工单 → 工单释放 → 仓库生产领料 → 生产执行/报工`

- 备料申请提交时系统按当前可用库存形成“不预留、不占用”的覆盖快照，缺口幂等转采购。
- 仓库不受理计划备料申请。真实库存分配和生产领料任务只在工单释放时形成。
- 工单释放重新校验库存；评估时可覆盖不等于释放时仍可覆盖。

### 3.4 生产质量与完工入库

`开工首检/过程检 → 报工 → 包装 → 入库抽检 → 质量放行 → 仓库完工入库`

- 质量判定只改变可继续生产、可包装、可入库或需处置的门禁，不直接增加库存。
- 质量放行幂等确保仓库完工入库任务；仓库正式过账后才形成成品库存和流水。
- 不合格数量进入返工、复检、让步、报废或其他受控处置，不能被综合状态覆盖。

### 3.5 售后异常

- 销售/采购负责登记问题、方案和商务结果；仓库、质量、生产分别完成本模块物理任务。
- 仓库拒收或来料质检不合格可生成采购售后来源；退货、补发、换货或返工后的到场继续复用采购入库主链。
- 售后不生成财务执行任务。金额、日期、备注组成的商务记录不是会计凭证。

## 4. 页面与输出冻结

- 列表统一使用模块标题、搜索/筛选/排序/导出、4–6 个判断列、右侧生命周期与下一步；760px 以下转业务卡片。
- 详情统一使用顶部上下文、本模块动作、当前待办、左侧事实与明细、右侧状态/附件/日志。
- 跨模块来源默认纯文本；只允许当前模块内下钻。权限守卫继续拦截直接 URL。
- 报价单、销售订单和采购订单可以保留经过专门设计的对外输出。
- 采购申请、仓库作业、售后、生产和质检属于内部执行与审计页面，不使用通用浏览器打印/PDF。未来若需要工单流转卡、检验报告或合格证，应分别建立明确模板和权限。

## 5. 当前兼容层清单

| 兼容项 | 当前合同 | 删除条件 |
| --- | --- | --- |
| `/api/finance/**` | 固定返回 `410`，提示在销售/采购订单登记轻量商务进度 | 历史演示财务数据导出完成、无旧客户端访问 |
| `/api/production/material-requests/:code/accept` | 固定返回 `410`；生产提交时已自动评估和分流 | 所有旧“待仓库受理”数据迁移完成、无旧客户端访问 |
| `/api/sales/outbound-requests` | 保留为销售交付向仓库出库的内部承接合同，不作为销售菜单页面 | 数据库中由 `ShipmentHandoff / SalesIssueTask` 等价承接后再评估 |
| 旧复合 `status` 与字段别名 | 只用于读取迁移和投影；新命令不得继续扩展旧枚举 | 数据迁移到独立生命周期、数量和责任字段后删除 |
| `availableQty / purchaseQty` | 生产备料评估的原型别名，分别对应库存覆盖和采购缺口 | 数据库迁移为 `inventoryCoveredQty / purchaseGapQty` |
| `source = legacy` 商务记录 | 历史迁移记录只读，不允许删除 | 历史来源与审计迁移完成后保留为普通只读事件 |

兼容接口必须记录访问量。数据库切换后的一个稳定发布周期内访问量为零，才能物理删除；不能仅因菜单隐藏就假设没有旧调用方。

## 6. JSON 原型不能带入数据库的实现方式

- `mutationQueue` 把所有请求全局串行化，只能降低单进程原型写冲突，不能替代数据库事务、行锁和并发唯一约束。
- `writeData` 的临时文件重命名提供单文件替换，不支持多实例写入、部分表锁、外键或提交回滚。
- 读取时扫描并修复历史数据只适合演示迁移；数据库阶段改为有版本号、可重复执行且有校验报告的离线迁移。
- 前端静态样本与 API 持久化数据混合只用于原型兜底；数据库切换后运行页面只读 API，样本进入测试夹具。
- 当前列表主要在客户端搜索、排序和分页；数据库接口必须提供服务端筛选、稳定排序、游标或页码及真实总数。
- 当前附件多为元数据；正式环境应将文件放对象存储，数据库只保存文件标识、哈希、大小、类型、来源和访问权限。

## 8. 关键唯一约束

- 所有单据 `code` 在各自类型内唯一；编号分配在事务中完成。
- 所有业务行拥有稳定 `line_id`，来源承接必须引用来源行，不只引用整单。
- `inventory_fact` 唯一键：`company_id + warehouse_id + location_id + material_id + batch_key`；免批次使用明确非空 `batch_key`，不能依赖数据库对 `NULL` 唯一性的差异。
- 一个有效 `source_type + source_document_id + source_line_id + occupation_type` 只能形成一条活动库存占用。
- 一个生产释放只能有一张活动生产领料任务。
- 一个质量放行来源只能有一张活动完工入库任务。
- 一个销售交付来源在同一续建序号下只能有一张活动销售出库任务。
- 一个生产备料申请最多关联一张活动缺口采购申请：`purchase_requisition.source_material_request_id` 建活动记录唯一约束。
- 同一检验来源、检验类型和触发事件最多形成一张活动质检任务。
- 幂等键按 `tenant/company + command_type + source_document + idempotency_key` 唯一。
- 库存流水、审计日志和已提交业务事件不可更新、不可删除；纠错使用反向事件。

## 9. 必须事务化的命令

| 命令 | 同一事务内必须完成 |
| --- | --- |
| 确认销售订单 | 冻结订单快照、形成/更新销售预留和生产需求来源、写事件与审计 |
| 生成/同步交付安排 | 保存交付事实、幂等确保仓库销售出库任务、写通知 |
| 确认销售出库 | 锁定库存行、校验并扣减实物/合格、消费预留、写流水、完成任务、回传交付 |
| 提交生产备料申请 | 冻结申请、读取可用库存快照、写覆盖明细、幂等生成缺口采购申请 |
| 释放生产工单 | 锁定库存行、创建生产分配、保存释放、幂等生成仓库领料任务 |
| 确认生产领料/退料 | 更新库存与生产分配、写流水、完成仓库任务、回传生产 |
| 确认采购到场 | 冻结实收/拒收事实、增加待检或待入库受控量、幂等生成来料质检任务 |
| 提交质量判定 | 保存逐行/逐项结果与决定、移动质量受控数量、形成处置或仓库交接事件 |
| 正式采购/完工入库 | 锁定受控数量、增加正式库存、生成/承接批次、写流水、完成任务并回传 |
| 调拨发出/接收 | 来源扣减、目标在途增加或清除、目标正式库存增加、写两端流水 |
| 开始/确认盘点 | 冻结范围与快照；确认时写差异事件、更新库存并解除冻结 |
| 库存冲销 | 校验原事件未冲销，生成等量反向事件，更新余额并双向关联 |
| 登记/删除商务进度 | 写软删除事件、重算订单聚合与状态、写审计 |

事务失败必须整体回滚，不能出现“单据完成但库存未变”或“库存已变但流水/来源缺失”。

## 10. 并发与锁策略

- 库存扣减、分配、冻结、盘点和调拨使用确定顺序锁定 `inventory_fact` 行，避免跨多行死锁。
- 订单、工单、仓库任务和质检任务使用版本号做乐观并发；提交时校验 `version`，冲突返回可重试错误。
- 编号、来源唯一任务和幂等命令依赖数据库唯一约束处理竞争，不能先查询再假设无人插入。
- 采购/销售来源行累计承接在事务中锁定来源行并重算有效承接，防止并发超量。
- `outbox_event` 与业务事务同提交，异步通知失败不回滚业务事实，但可重试且不重复发送。

## 11. 数据迁移顺序

1. 停止扩张原型字段，保存 JSON 快照、文件哈希和回归版本。
2. 清理历史财务不可达数据、旧状态别名和前端静态兜底样本，输出迁移映射报告。
3. 先迁移公司、单位、物料、仓库/库位、客户、供应商、员工和权限。
4. 迁移销售、采购、生产、质量和仓库单据头/行，生成稳定内部主键并保留原编码。
5. 把复合状态拆为生命周期、数量、责任和交接事实；旧状态只写入迁移审计。
6. 迁移批次、库存余额、占用来源和流水。以原型余额作为期初事件，验证每个库存键的期初加事件等于余额。
7. 迁移活动仓库任务、质检任务、生产释放和售后任务，建立来源唯一约束。
8. 迁移附件元数据、日志、通知和轻量商务记录。
9. 启用外键、检查约束和唯一约束，运行数量守恒与孤儿来源报告。
10. 使用只读影子接口对比 JSON 与数据库投影；五模块回归全部一致后切换写入。
11. 切换后保留 JSON 只读归档，不再双写；观察兼容接口访问量后按删除条件清理。

## 12. 数据库开工门禁

以下条件全部满足后才开始建正式 schema：

- 两份权威文档和本冻结清单没有未决流程冲突。
- `build`、`audit:ui`、`smoke:frontend`、销售、采购、仓库、售后、生产短关和完整业务流回归通过。
- 生产、采购、仓库、质量代表账号完成桌面角色边界验收。
- 五模块关键列表/详情在 760px 以下完成代表性验收，主状态、数量、风险和主动作不丢失。
- 两个 `410` 兼容接口及保留的内部销售交接接口已经登记删除或保留策略。
- 正式样本中不存在重复库存键、重复活动来源任务、负库存、占用大于合格库存或来源孤儿。
- 数据库引擎、备份恢复、对象存储和部署方式单独确认；本文件不提前绑定产品。
