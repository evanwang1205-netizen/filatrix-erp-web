# Filatrix ERP Web 销售、采购、仓库逐页实跑审计（2026-07-29）

## 1. 审计目标

本轮不以保护演示数据为约束，直接使用可增删、可冲销、可拒收的一次性样本，复核销售、采购、仓库三个角色的：

- 菜单与直接 URL 权限边界；
- 列表字段、状态、下一步和搜索/排序/筛选/导出；
- 详情、新建、编辑、跟进和异常页的统一骨架；
- 保存、确认、提交、删除、作废、拒收、冲销和库存过账；
- 原生确认弹窗与未保存离开提醒；
- 740px 窄屏下的操作可达性和信息完整性。

销售账号只能操作销售，采购账号只能操作采购，仓库账号只能操作仓库。关联记录允许显示来源编号和结果，但不得把其他岗位的执行入口伪装成本岗位动作。

## 4. 本轮发现并修复

1. 采购入库已选择两条分仓明细，保存时仍按旧的逐行目标仓字段校验，导致误报“请选择正式入库仓库”。服务端现保存 `inboundAllocations` 草稿，并仅对旧请求执行兼容校验。
2. 采购正式入库流水曾被归类成“到货待检”。流水分类现在优先识别“采购正式入库”为“采购入库”。
3. 到货整行拒收曾错误显示“待质检/质检冻结/待生成质检任务”。现固定为“未送检（到货拒收）/仓库当场拒收/不入库”，且不生成质检任务。
4. 采购售后选择补发、换货或返工后，曾可在统一采购入库未完成时提前提交结果。现以补救收货任务为强制协同门槛。
5. 历史调拨单没有保存 `toLocation` 时，详情显示“系统默认库位”，尽管库存实际进入 `FG-AUTO`。现从在途目标库存键补齐显示，未来调出时也持久化真实目标库位。
6. 调拨详情的两列跨格字段导致三列事实网格留下灰色空单元。只读详情改为六个等宽事实，编辑态仍保留长原因输入。
7. 采购订单已经完成入库但主状态仍为“已确认”时，顶部事实写“跟进供应商开票”，按钮却写“等待仓库处理”。动作派生现优先读取进度事实，再使用生命周期状态兜底。
8. 收票、付款和开票引导仍写“参考号”，与轻量商务登记合同冲突。现统一为“金额、日期、备注”，不要求编号或附件。
9. 售后页面继续把兼容字段标成“财务处理”。独立财务模块退出后，页面统一改称“商务调整”；字段名只为已有数据兼容。
10. 多个成功的保存、确认、提交、删除和过账动作没有重置未保存基线，导航时会误弹提醒。销售报价/订单、采购申请/订单、采购入库、销售出库和通用仓库单据都在成功动作后重置基线。
11. 销售账号可通过采购收票候选接口读取采购发票明细，违反模块边界。`purchase-invoices` 候选接口现要求采购编辑权限，销售实测返回 `403`，采购仍可正常读取。
12. 通用 API 回归仍依赖固定样本状态、已删除物料/仓库、旧财务账号和过期流程字段。测试现改为读取当前快照、使用接口返回编码、遵守采购暂存仓与现行确认必填项，并把独立财务读写固定验收为 `410`。

## 5. 弹窗验收合同

- 未保存提醒选择“取消”必须留在当前页并保留输入；
- 未保存提醒选择“确定”才允许离开；
- 删除、作废、拒收、冲销和过账若出现原生确认，自动化执行者必须读取并亲自选择，不把弹窗留给用户；
- 业务动作成功并建立新基线后，不得紧接着再次弹出未保存提醒；
- 删除验证同时覆盖取消后记录仍存在、确认后记录删除；
- 本轮全部弹窗均由 Codex 处理，没有把页面停在确认阶段交给用户。

## 6. 视觉与响应式结论

- 列表统一使用标题栏、搜索、排序、筛选、导出、正文/状态或移动卡片、分页；
- 交易详情统一使用顶部动作、当前待办、左侧业务正文、右侧状态与关联记录；
- 详情只读事实网格的同行字段共同增高，不再以灰色空格补位；
- 销售和采购跟进把关联记录放在右侧进度下方，左侧保留可持续阅读的履约与商务事件；
- 采购入库等内部仓库作业不提供打印/PDF；
- 740px 实测覆盖销售订单列表/跟进、采购订单列表/跟进、采购入库列表/详情、库存查询；主动作、主状态、数量和风险均保留，无整页横向溢出。

## 7. 数据库阶段保留事项

当前仍是 JSON 单进程原型。正式数据库必须把库存移动、来源数量累计、收货/质检/入库、调拨两段、盘点冻结与差异、售后补救门槛、冲销和审计流水纳入事务、唯一约束、乐观版本与幂等命令。测试样本可以删除，但本审计中的数量守恒和角色边界必须成为集成测试。

## 9. 第二轮逐页复核补充

本轮重新按销售、采购、仓库三个角色进入全部可见列表、详情、跟进、异常和库存页面，重点复查第一轮修正后的派生结果、跨模块入口、列表摘要和消息投影。补充发现并修正：

1. 销售订单跟进曾把已经冲销的出库单继续累计为已发货，导致 `SO-20260712-018` 错显“已发完 / 100%”。已发数量现只累计 `status = 已出库` 且无 `reversalCode` 的记录；待出库和已冲销分别展示。
2. 销售、采购售后详情曾把仓库和质量处理记录渲染成可点击入口，但角色守卫会立即拦截。关联记录仍完整显示编号、状态和结果，同模块记录可追溯，跨模块记录改为不可点击的只读事实。
3. 资产采购跟进曾让采购人员点击“建立资产档案”并跳到无权访问的基础资料页面。资产验收仍由采购完成，资产档案由拥有基础资料维护权限的责任人建立；采购页面只显示“等待资产档案登记”和回写结果。
4. 整行拒收的采购入库任务曾按接收量显示 `0 kg`，掩盖真实到场和拒收数量。列表现优先显示“到场、接收、拒收、异常暂收”数量语义，`WR-20260728-001` 显示为“到场 1 kg · 拒收 1 kg”。
5. 仓库售后和库存流水曾直接显示 `ACC-WAREHOUSE` 等技术账号。页面现统一投影业务人员名称，技术标识只保留在内部数据和审计键中。
6. 通用“库存已过账”通知曾把调拨、其他出入库等仓库内部动作发送给销售和采购。通知现按来源任务路由：销售出库只通知销售、采购入库只通知采购，调拨和其他移动只通知仓库；来源已冲销时原成功通知失效，并生成对应冲销结果。

第二轮修正后再次通过 `node --check server/index.mjs`、生产构建、`161` 项 UI 审计、`smoke:frontend`，以及销售、采购、仓库、售后和完整业务流专项回归。浏览器复验确认销售未发数量、拒收数量、资产建档边界、售后关联记录和三角色通知均与权威业务事实一致。

## 10. 第三轮交易细化复核补充

第三轮不再扩展流程，改为核对“按钮是否真能执行、日期是否来自正确事件、跨单据列表是否混入同源订单的其他记录、历史流水是否被样本初始化覆盖”。补充发现并修正：

1. `SO-20260712-018` 只有 `80 / 160 卷` 完成出库时，页面仍从订单旧状态 `待签收` 派生整单“签收”按钮，服务端执行必然拒绝。存在结构化交付进度时，整单签收现在只由交付事实 `待签收` 决定，不再回退旧状态；待处理记录统一命名为“出库任务”，避免与已完成出库流水混淆。
2. 历史回款记录缺少 `settledAt` 时曾错误回退应收截止日，导致页面把 `AR-20260717-002` 显示为 `2026-08-16`。旧记录现在按实际登记日、更新时间、最后才到期日的顺序迁移，销售跟进复验显示 `2026-07-17`。
3. 新增销售/采购开票、收票、回款、付款登记允许填写未来日期。前端日期上限和服务端校验现统一为上海业务日期，避免预登记被当作已经发生的商务事实。
4. 生产缺料自动生成的采购申请可能出现“申请日期晚于采购需求日期”。系统现在保留原生产需求日 `sourceExpectedDate`，同时把采购可执行需求日期归一到不早于申请日；详情明确显示来源日期及生成时已逾期说明。
5. 采购售后右侧关联记录曾混入同一采购订单下的全部收货和来料质检。存在来源拒收单或补救收货时只投影两条处理链及其质检记录；纯手工旧售后没有任何来源收货时才回退订单级关联。
6. 资产采购列表曾只显示预计到货 `2026-08-10`，掩盖已经发生的实际到货 `2026-07-29`。列表主字段现为实际到货日期，预计日期作为对照信息。
7. 历史销售出库和冲销流水的经办人仍为“待分配”，且冲销请求可从正文伪造操作人。过账和冲销统一取当前认证账号投影业务人员；历史记录由审计事件恢复，库存流水复验为“王倩”。
8. `WR-20260712-001` 的待检、待入库流水在迁移后仍会被仓库黄金样本再次覆盖回“原料仓”。读取顺序现保留既有生产分配样本，并在仓库样本补齐后再次执行采购暂存迁移；两条历史流水稳定归属 `采购暂存区 / QC-AUTO`。

第三轮浏览器复验覆盖销售跟进、采购申请、资产采购、采购售后和库存流水；销售部分出库不再暴露死按钮，采购日期与关联范围正确，仓库历史暂存和经办人正确。最终通过 `node --check`、生产构建、`162` 项 UI 审计、销售、采购、售后、仓库、商务登记、前端及完整业务流回归。

## 11. 第四轮库存事实与采购追溯复核补充

第四轮从库存查询的物料汇总反查到采购到货、来料质检、正式入库、库存流水、补货预警和采购售后，重点核对“同一实物是否只算一次、各受控状态是否合计回物理数量、流水是否能解释当前余额”。补充发现并修正：

1. `PETG-260712-A` 同时存在于 `采购暂存区 / QC-AUTO` 与 `原料仓 / RM-01-03`，同一 `1,000 kg` 被库存查询计算两次。黄金样本和读取迁移现统一保留暂存事实并删除正式仓副本。
2. `IQ-20260712-001` 判定的 `80 kg` 不合格数量没有独立进入库存模型，使物理数量与合格、待检、待入库之间出现无法解释的差额。新增不合格隔离事实后，该批次分区为待检 `270 kg`、待入库 `650 kg`、不合格 `80 kg`。
3. 采购库存流水缺少物理到货、质检冻结的反向解除、待入库正式转出和不合格隔离事件。现有历史数据幂等补齐，新增动作同步写入，不再只能看到增加而看不到受控数量减少。
4. 正确把待入库实物留在采购暂存区后，原料仓补货预警曾可能漏掉这部分已放行数量。预警改为按采购收货行的正式目标仓投影，PETG 仍得到 `160 + 650 = 810 kg` 预计库存。
5. 来料质检读模型仍使用旧名称“质检暂存区”。现跟随来源收货统一显示“采购暂存区”，避免同一物理区域出现两个名称。
6. 读取迁移在数据净值未变化时仍会更新根 `updatedAt`，导致每次 GET 都重写 JSON。现先比较归一化快照，仅真实变化时写入。
7. 采购售后旧样本缺少 `sourceReceipt / qualitySourceCode`，生成补救收货后右侧关联只剩补救链。唯一不合格来源迁移现补齐原始收货与质检，采购专项回归恢复通过。
8. 旧库存流水只保存文本 `-80 kg`、没有 `quantityNumber` 时，待入库转出兼容补写曾生成 `+0 kg`。迁移现从文本恢复结构化数量并修正已生成的零值事件；流水类型优先显示明确的“采购到货、质检冻结、质检解冻、待入库转出”，不再把物理到货和质检冻结都笼统写成“到货待检”。

本轮隔离实跑重新完成“采购到货 → 质检冻结 → 全数放行 → 40% 入原料仓 → 60% 入包材仓”，核对物理到货、质检解冻、待入库转出和目标仓合格入库四类流水总量一致；同时通过销售、采购、仓库、补货和完整跨模块流程回归。
