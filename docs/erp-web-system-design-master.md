## 1. 文档目的

本文件负责回答四个问题：

1. Filatrix ERP 要服务哪些角色和业务目标；
2. 每个模块负责什么、不负责什么；
3. 模块之间按什么事实和单据协作；
4. 设计、前端实现和底层联动按照什么顺序进入。

本文件不替代业务事实模型。库存、数量、金额、来源行、承接数量、质检冻结、单据状态拆分等数据口径，继续以业务事实模型为准。

## 2. 已确认的项目决策

以下内容属于当前最高优先级决策：

- 先设计业务流程、逻辑、功能、页面内容和布局，再修改前端。
- 页面和按钮未确认前，不继续扩展依赖临时界面的底层业务命令。
- 整体设计先覆盖全系统；详细设计按模块逐个展开，不追求一次性把所有细节设计到最终状态。
- 模块设计顺序为：基础资料 → 销售 → 采购 → 仓库 → 财务 → 生产与质检 → 电商 → 首页、报表和系统完善。
- 生产模块现阶段暂停继续优化；已有实现保留为技术资产，但不能反向决定最终页面。
- 首页视觉和系统管理页面最后完善；导航框架、页面规范、权限边界和审计要求仍需提前设计。
- 界面质感是重点验收项：通过清晰层级、克制配色、舒适留白、稳定对齐和合理信息密度实现，不依赖装饰堆叠。
- “主状态承担过多含义”是重点整改项：主状态、库存、质检、供应、履约、财务和异常必须按事实拆分；该重点不降低其他流程、字段、权限和异常规则的重要性。

## 3. 产品目标

Filatrix ERP Web 的目标不是把所有信息堆到一个页面，而是让不同岗位快速完成三件事：

1. 判断当前业务处于什么状态；
2. 明确当前由谁处理、下一步是什么；
3. 从结果追溯到来源单据、明细行、数量和操作记录。

最终系统应具备以下特征：

- 一套主数据被所有模块引用，不在各模块重复维护客户、供应商、物料和仓库。
- 一套业务事实支撑列表、详情、工作台、首页和报表，不为每个页面编造独立状态。
- 跨模块交接通过明确单据和承接关系完成，不依赖口头说明或模糊综合状态。
- 页面操作只处理本模块职责；其他模块的结果以摘要和下钻入口呈现。
- 正常流程、部分完成、异常、撤销和反向处理都能说明事实发生了什么。

## 4. 用户角色

| 角色 | 核心任务 | 主要模块 |
| --- | --- | --- |
| 管理层/厂长 | 查看交付、库存、资金、质量和生产风险，处理跨部门阻断 | 首页、报表、销售、生产、财务 |
| 销售 | 报价、确认客户需求、跟踪交付、售后和回款状态 | 销售 |
| 采购 | 承接采购需求、选择供应商、跟踪到货、退换与价格 | 采购 |
| 仓库 | 收货、出库、调拨、盘点、批次与库存追溯 | 仓库 |
| 财务 | 开票、收票、应收应付、收付款和核销 | 财务 |
| 生产计划/厂长 | 确认生产需求、排产、建工单、释放和异常协调 | 生产 |
| 班组长/现场人员 | 领料、开工、报工、暂停、交接和异常上报 | 生产工作台 |
| 质检 | 来料、生产、巡检、不良判定和处置 | 质检 |
| 电商运营 | 店铺、SKU 映射、订单导入、发货回传和平台对账 | 电商 |
| 资料管理员 | 维护跨模块引用的稳定业务资料 | 基础资料 |
| 系统管理员 | 账号、角色、权限、菜单、编号、字典、通知和日志 | 系统 |

角色用于确定页面信息和操作边界，不等同于最终权限配置。一个账号可以拥有多个角色。

    B --> C["履约与库存层<br/>收货、质检冻结、入库、预留、出库、调拨"]

    C --> E
    D --> E
    F["渠道层<br/>电商平台订单、SKU、发货和对账"] --> B

页面可以按模块划分，业务事实不能被模块割裂。

## 6. 模块责任边界

| 模块 | 主要输入 | 本模块负责 | 主要输出 | 不负责 |
| --- | --- | --- | --- | --- |
| 基础资料 | 组织和业务规则 | 维护稳定引用对象、默认值和使用状态 | 可被业务单据引用的主数据 | 业务审批、库存数量、交易结果 |
| 销售 | 客户需求、成品和价格信息 | 报价、订单、交付承诺、交付追踪和销售售后 | 确认的客户需求、出库需求、开票/回款待办 | 仓库过账、生产执行、财务收款 |
| 采购 | 内部采购需求、供应商与价格 | 采购申请、物料/资产采购、到货跟踪和采购售后 | 采购承诺、收货需求、收票/付款待办 | 仓库入库、质检判定、财务付款 |
| 仓库 | 收发货需求、工单和质量放行 | 收货、入库、出库、领退料、调拨、盘点和台账 | 库存事实和库存流水 | 采购谈判、质量判定、生产报工 |
| 财务 | 已确认业务、发票和资金信息 | 销售/采购发票、应收应付、收付款和核销 | 结算事实和财务状态摘要 | 替业务部门关闭订单或库存作业 |
| 生产 | 销售缺口、备库需求、物料与工艺 | 生产任务、备料、工单、释放、现场执行和异常 | 领料需求、质检任务、完工入库需求 | 采购下单、仓库过账、质检放行 |
| 质检 | 到货、生产批次、巡检或客户反馈 | 标准快照、检验、判定、处置和复检 | 放行、隔离、退货、返工等质量事实 | 仓库过账、采购退款、生产报工 |
| 电商 | 平台店铺、商品和订单文件 | 渠道映射、导入导出、回传和对账 | ERP 销售需求与平台反馈 | 建立平行销售、库存和财务体系 |
| 首页 | 各模块待办与风险事实 | 按角色聚合下一步和风险 | 下钻入口 | 直接完成复杂业务操作 |
| 报表 | 统一业务事实 | 分析、对比和源单下钻 | 指标与趋势 | 保存、审批、过账 |
| 系统 | 组织、岗位和管理规则 | 账号、权限、菜单、编号、字典、通知和日志 | 系统配置与审计能力 | 业务单据和业务结果维护 |

## 7. 全系统共享规则

以下规则在详细设计时不得由单个页面自行改写：

### 7.1 主数据引用

- 单据保存主数据引用及必要快照，不能只保存一段名称文本。
- 停用主数据不能用于新单据，但历史单据仍可查看。
- 客户、供应商、物料、人员、仓库使用可搜索引用选择。
- 分类、物流方式、付款方式等固定选项由统一字典维护，业务页面只负责选择。

### 7.2 数量和金额

- 所有可计算数量必须包含数值、单位、基础单位数量和换算关系。
- 所有金额必须区分币种、含税方式、税率、税额、未税和含税金额。
- 页面展示可以组合单位和货币符号，计算和存储不能依赖组合字符串。

### 7.3 来源和承接

- 跨单据关系必须落到来源单据行、目标单据行和承接数量。
- 合并、拆分、部分交付、部分入库和部分核销都使用同一承接口径。
- 页面优先显示业务结果，例如“需求 100 件，库存承接 20 件，生产承接 80 件”。

### 7.4 状态

- 主状态只表示当前单据生命周期。
- 到货、质检、入库、交付、生产、开票、收付款和异常分别保存事实维度。
- 列表显示的状态和下一步由事实派生，不能作为用户随意编辑的业务事实。

### 7.5 库存

- 可用库存统一按“在库合格 - 已预留 - 已分配 - 冻结”计算。
- 到货、待检、待入库、在途不能冒充可用库存。
- 预留不等于出库，质检放行不等于仓库入库。

### 7.6 操作和审计

- 每个页面只保留一个主要动作，低频动作进入更多菜单。
- 禁用动作必须说明缺少什么条件或权限。
- 保存、确认、过账和核销等操作防重复提交。
- 已进入跨部门流转的单据原则上不物理删除，采用作废、关闭、冲销或反向单据。

## 8. 设计与实施方法

每个模块必须依次通过五个门：

| 阶段 | 产物 | 通过条件 |
| --- | --- | --- |
| D1 流程确认 | 正常流程、异常流程、角色、跨模块交接点 | 用户能确认业务如何运行 |
| D2 功能确认 | 对象、功能清单、状态、规则、权限边界 | 无明显职责重叠或缺口 |
| D3 页面确认 | 页面清单、内容、布局、字段、按钮和状态 | 页面规格可直接指导前端 |
| D4 前端验收 | 浏览器中的桌面/窄屏原型 | 用户确认可用并标记冻结 |
| D5 联动实现 | 必要接口、状态变化、来源追溯和测试 | 冻结页面的业务结果真实可验证 |

未通过 D3 的模块不进入前端大改；未通过 D4 的页面不继续扩展底层联动。

## 9. 模块推进顺序

| 阶段 | 模块 | 设计重点 | 退出条件 |
| --- | --- | --- | --- |
| 0 | 全局设计 | 系统总纲、跨模块流程、页面规范、权限边界 | 本设计包完成首次评审 |
| 1 | 基础资料 | 主数据边界、默认值、引用方式、主数据页面模板 | 基础资料页面与字段冻结 |
| 2 | 销售 | 报价、订单、库存/生产承接、交付和售后 | 销售页面与交接点冻结 |
| 3 | 采购 | 申请、物料/资产采购、到货和采购售后 | 采购页面与交接点冻结 |
| 4 | 仓库 | 收货、入库、出库、调拨、盘点、库存台账 | 库存口径和作业页面冻结 |
| 5 | 财务 | 发票、应收应付、收付款和反向链 | 结算页面和来源关系冻结 |
| 6 | 生产与质检 | 任务、工单、执行、质量判定和完工 | 制造质量页面与现场工作台冻结 |
| 7 | 电商 | 渠道映射、订单、库存、发货、售后和对账 | 渠道复用主流程得到验证 |
| 8 | 首页、报表、系统 | 角色待办、分析、权限配置和审计页面 | 全系统入口和管理闭环完成 |

阶段顺序是设计和改造顺序，不代表企业实际业务只能按这个顺序运行。

## 10. 设计状态管理

每项设计使用以下状态：

- 草案：已有思路，尚未系统检查；
- 待评审：文档完整，可以由用户确认；
- 已确认：流程和页面方向已确认，可以开始前端；
- 已冻结：按钮、内容和布局已经浏览器验收，后续变更需要记录原因；
- 已实现：前端与必要联动已经完成；
- 已验证：通过浏览器、流程和构建检查。

历史代码、已有接口或已通过测试不自动等于“已确认”或“已冻结”。

## 11. 当前待确认事项

以下问题会在对应模块详细设计时确认，不阻塞当前总纲：

1. 销售订单确认后是自动预留库存，还是生成待仓库确认的分配建议；
2. 销售缺货是否自动创建生产任务，还是先进入生产待确认队列；
3. 采购申请是否需要金额或类别分级审批；
4. 仓库收货和正式入库是否由同一岗位完成；
5. 财务是否在首版体现采购三单匹配；
6. 来料让步放行、超收、超领和负库存的授权规则；
7. 电商订单是否全部生成 ERP 销售订单，还是允许按店铺/批次汇总。

所有待确认问题先记录默认建议和影响页面，不能通过临时代码静默决定。

## 12. 当前下一步

基础资料流程和内容方案已确认，物料样板已进入浏览器验收：

1. 验收物料列表、详情和编辑页的视觉层级、内容密度与操作入口；
2. 验收“使用状态只控制新业务引用，供应、库存、质量分别记录事实”的状态拆分；
3. 用户确认物料样板后，将同一设计语言推广到客户和供应商；
4. 再依次完成公司/部门/单位、仓库/员工、资产/产线；
5. 基础资料页面冻结后进入销售模块详细设计和前端实现。
